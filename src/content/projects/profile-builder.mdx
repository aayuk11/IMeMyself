## The problem

Profile Builder is where our analysts create and update profiles of politically exposed persons (PEPs) and their relatives and close associates: more than 35 million records that clients rely on for compliance checks.

The data was strong. The tool wasn't. It ran on old .NET and JavaScript pages, work was spread across many screens, analysts exported to Excel for bulk edits, and it was hard to tell whether an incoming profile was new or a duplicate.

## What I did

I led the rebuild end to end: analyst interviews, PRDs and FRDs, sprint grooming, stakeholder management, releases, testing and UAT.

| Area | Before | After |
| --- | --- | --- |
| Tech | Old .NET and JavaScript pages | React and the latest .NET |
| Screens | Many separate pages | Fewer pages, redesigned UI |
| Search | Basic | Global search, filtered results in under 2 seconds |
| Tables | Exported to Excel for bulk edits | Edit, filter and bulk-update in place |
| Data | Tied to the old pages | Served through APIs |
| Duplicates | Hard to spot | Checked before a profile is added |

Every profile now moves through one tracked workflow, with an owner at each step.

I also wrote the requirements for an AI pipeline that fills in profile details from public sources. Every value keeps its source, and anything the AI isn't sure about goes to an analyst for review.

## Results

Analysts now create and update profiles in one modern tool, with fewer pages, faster search and bulk edits built in. Every change is tracked from creation to delivery.

## What I'd do differently

I specced the new tables before I understood why analysts were exporting to Excel. I assumed it was habit. It wasn't: they needed bulk edits the old tables couldn't do. Now I ask what people do in their workaround before deciding what to build.
