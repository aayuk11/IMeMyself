## A month of configuration before the first alert

Transaction monitoring is only as good as its rules. For every new client — a bank, an NBFC, a crypto exchange — our implementation team translated regulatory typologies into detection logic by hand, then wrote test data to prove each rule fired when it should and stayed quiet when it shouldn’t.

That took about a month per client. Sales could close faster than we could configure, so the ceiling on growth wasn’t demand. It was how many rules a small team could write and verify.

## A workflow that writes rules, and a system that doesn’t trust it

I designed and built a generative AI workflow in Claude Code that takes a regulatory scenario in plain language and produces a production rule in our YAML DSL, positive, negative and edge-case test data, and a deployment package. A Source of Truth layer runs a similarity search first, so we extend coverage instead of duplicating it.

1. **Retrieve.** Similarity search over the existing library. A match means reuse, not regenerate.
2. **Generate.** The LLM drafts the rule and its test data.
3. **Validate.** Schema, golden regression, generated tests. Fail any one and it goes back to 02.
4. **Deploy.** Production, with an audit trail.

> “The model was never the risky part. The risk was a plausible-looking rule that silently missed a typology.”

## What I’d do differently

I built the golden regression suite after the first hundred rules, not before. Next time the evaluation harness ships first, and the generator earns its way in against it.
