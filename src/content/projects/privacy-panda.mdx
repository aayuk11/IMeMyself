## The problem

India's Digital Personal Data Protection (DPDP) Act 2023 requires every company that holds personal data to collect consent properly, let people see, correct or delete their data, and prove all of it to a regulator. Almost no tools existed for this, and no engineers were allocated to build one.

## Finding the solution

A compliance product has two very different users, and they want opposite things:

- **Individuals** want to see, fix or delete their data and withdraw consent, quickly. If it's hard, they give up, and an abandoned request is itself a compliance failure.
- **Companies** want control, approvals and proof of every action, so they can show a regulator they complied.

One screen for both would be too heavy for individuals and too loose for companies. So I designed two portals, each built for its user, on one shared system underneath.

## Building the prototype

With no engineers, I built it myself.

1. **Started small.** A basic working version first, to learn which features mattered and which were assumptions.
2. **Mapped the law to features.** Every requirement in the Act became a product feature, so nothing rested on guesswork.
3. **Wrote the specs.** User flows for both portals, personas, the PRD, and a 58-endpoint API that keeps each client company's data separate from day one.
4. **Built it in stages.** Against my own specs, with Claude Code and Antigravity, so leadership could click through a real product instead of reading a deck.
5. **Got it approved.** The executive team approved the prototype as the base for the engineering build.

I also set up PostHog tracking from day one, so the build can be planned around where people actually drop off.

## Results

- A working two-portal product covering the core DPDP requirements.
- Approved by the executive team as the base for the engineering build.
- Specs complete enough for engineers to build from.
- Several decisions in the final spec came from what the prototype showed didn't work.

## What I'd do differently

My first version put consent and data requests in one flow, because the Act groups them. In use they're very different: consent is given once, while a request has a deadline and a status people want to check. I split them, but later than I should have.
