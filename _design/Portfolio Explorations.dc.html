01 — The problem

A month of configuration before the first alert

Transaction monitoring is only as good as its rules. For every new client — a bank, an NBFC, a crypto exchange — our implementation team translated regulatory typologies into detection logic by hand, then wrote test data to prove each rule fired when it should and stayed quiet when it shouldn’t.

That took about a month per client. Sales could close faster than we could configure, so the ceiling on growth wasn’t demand. It was how many rules a small team could write and verify.

Compliance teams felt it most: a month of paying for a system that hadn’t raised a single alert.

02 — What I built

A workflow that writes rules, and a system that doesn’t trust it

I designed and built a generative AI workflow in Claude Code that takes a regulatory scenario in plain language and produces three things: a production rule in our YAML DSL, positive, negative and edge-case test data, and a deployment package.

Before anything is drafted, a Source of Truth layer runs a similarity search over the existing library, so we extend coverage instead of duplicating it.

03 — How it worked

Guardrails, not prompts, did the heavy lifting

The model was never the risky part. The risk was a plausible-looking rule that silently missed a typology. So every output passes schema validation, then a golden regression suite of known-good rules, then generated tests that must fire, must not fire, and must survive edge conditions.

Configuration time collapsed. The work a team used to do in a month now runs, with review, inside two days.

Two changes underneath mattered as much as the generator. Cross-account identity resolution, linking the same person across accounts, halved inference cost and lifted detection coverage by 10%. Automated SFTP ingestion across 40+ file formats removed manual onboarding entirely.

04 — Outcome

From one client to twenty in two months

1→20+clients in 2 mo <48hconfig, was 1 mo 500+prod rules −50%inference cost +10%detection coverage 40+file formats ingested

The delivery ceiling disappeared. Pre-sales could promise coverage and implementation could keep the promise — across banking, NBFC, insurance, housing finance, crypto and payments in India, the UK and Nepal. Sales now uses the Source of Truth in live demos to prove coverage before a contract is signed.

05 — What I’d do differently

Where I was wrong

I built the golden regression suite after the first hundred rules, not before. For those weeks, review was a person reading YAML — the exact bottleneck the system was meant to remove. Next time the evaluation harness ships first, and the generator earns its way in against it.

I also treated the Source of Truth as an internal tool. Sales adopted it for demos within weeks. Designed for that audience from day one, it would have had coverage reporting built in, not bolted on.

Guardrails are the product

The validation layer between an LLM and a regulated system matters more than the model behind it.

Aayush Kumar AI evaluation · RegTech

The first rule our model wrote for a client was wrong in a way that would have passed review. It flagged outbound transfers to new jurisdictions, exactly as asked, but counted the time window from the wrong timestamp. On the page it looked like a rule a senior analyst would write. In production it would have missed most of what it was meant to catch.

That rule is why I stopped thinking of the model as the product. In a regulated system, the product is the set of checks that decide whether anything the model says is allowed to matter.

Plausible is the failure mode

Language models are very good at producing output that looks correct. That’s useful when a person reads every line. It’s dangerous when the output is detection logic for a bank, where the cost of a quiet miss is a regulator’s finding rather than a bad answer.

So we designed the workflow backwards: start from what must never reach production, then let the generator fill in everything else.

“If a rule can’t prove it fires, it doesn’t ship. The model doesn’t get a vote.”

Three checks, in order

Every generated rule passes the same three gates. Each is cheap on its own; together they catch nearly everything a careful reviewer would.

  1. 01Schema validation. The rule must parse, reference fields that exist, and stay inside the DSL’s grammar.
  2. 02Golden regression. A suite of known-good rules re-runs on every change, so a new rule can’t quietly break an old one.
  3. 03Generated tests. Positive, negative and edge cases are written with the rule. It has to fire, stay quiet, and survive the boundaries.

The negative cases matter most. Asking the model to write the transaction that should not fire is the closest thing we have to asking it to argue against itself. It’s also where the timestamp bug surfaced: a test where value_date and created_at were three days apart.

What this changes for a PM

Most of my time on this project didn’t go into prompts. It went into deciding what “correct” meant, writing that down as tests, and getting compliance, engineering and QA to agree on it. That work looks like requirements gathering, because it is.

The model gave us speed. The guardrails are why anyone was willing to use it. I wrote about the delivery side of this in One month to 48 hours.
